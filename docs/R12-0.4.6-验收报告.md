## 1. 本次修了什么

`api_mode: anthropic_messages` 的用户在 Credential Guard 阻断一次请求时，
终端看到的是 **上游 API 故障**，而不是阻断原因。

真实端到端实测（隔离 profile，真实 anthropic_messages provider，
把 `credential-guard.json` 权限改成 644 触发 fail-closed）：

| | 修复前 | 修复后 |
|---|---|---|
| 主输出 | `Invalid API response after 3 retries: response time 21.0s` | `Credential Guard 已阻止本次请求`（完整六行中文诊断） |
| 原因码 | 被吞 | `代码：CG-CONFIG-UNAVAILABLE` |
| 外发声明 | 无 | `发送状态：未发送给外部模型。` |
| 退出码 | 1 | 0 |
| 耗时 | 约 20 秒（3 次重试空等） | 1.4 秒 |

**没有泄密**：修复前后 Provider 都是 0 次调用，阻断本身一直是有效的。
问题是把本地故障说成了上游故障，会把排查方向带偏 —— 真实原因可能只是
一句 `chmod 600`。

## 2. 根因

`_safe_blocked_response()` 只会构造 OpenAI `chat.completion` 形状（`.choices`）。
宿主 `AnthropicTransport.validate_response()` 要求 `.content` 是 list，
两边对不上 → 判定为无效响应 → 重试 3 次 → 报 `Invalid API response`，
真正的诊断连同响应体一起被丢弃。

实测取证（`/Users/yelei/tmp/cg-test/plan_evidence.py`，只读）：

| 编号 | 结论 |
|---|---|
| F1 | 修复前的阻断响应字段 `['choices',…]`，无 `.content`；Anthropic `validate_response` = **False** |
| F2 | 换成 Anthropic 形状后 `validate_response` = **True** |
| F3 | `normalize_response` 能完整还原中文诊断与原因码 |
| F4 | `api_mode` 确实在 kwargs 里（`conversation_loop.py:3187` 明写 `api_mode=agent.api_mode`） |
| F5 | `chat_completions` / `bedrock_converse` 对旧形状 = **True** → 只有 Anthropic 这条路是坏的 |

## 3. 改动

生产代码仅 `credential_guard/middleware.py`：

- 拆出 `_blocked_response_openai()` / `_blocked_response_anthropic()`
- `_safe_blocked_response()` 新增 `api_mode` 参数并分派
- `on_llm_execution()` 把宿主传入的 `api_mode` 透传下去

**透传这一步是必需的**：不做的话构造函数写得再对，生产环境里也不会被走到。
该点由独立测试与变异 M3 共同盯防。

## 4. 覆盖范围：加分支，不是收窄

用户口径（2026-08-24）：**下限是 `anthropic_messages` + `chat_completions`，
其余已经能用的一律保持原样，不刻意删除覆盖。**

| api_mode | 修复前 | 本次动作 | 修复后 |
|---|---|---|---|
| `anthropic_messages` | 坏 | 新增分支 | **修好** |
| `chat_completions` | 好 | 不动 | 不变 |
| `bedrock_converse` | 好 | 不动 | **保留覆盖** |
| `codex_responses` | 无法本地验证 | 不动 | 与修复前逐字节一致 |
| 未知/未来值 | 走默认 | 不动 | 走默认，行为不变 |

`codex_responses` 的准确表述是 **「不新增针对性适配」，不是「移除支持」**：
其 transport 在本机无法 import，适配未经验证的东西等于猜；本次它的行为与
修复前完全一致，既没变好也没变坏。

零退化由 `test_non_anthropic_shape_is_field_identical` 机器保证：
对照的是**从 0.4.5 手抄的字段预期表**，而非现算值，所以即便生产代码整体
漂移，这个对照依然有效。

### 5.2 宿主契约（真实 transport）

`scripts/run_r12_host_contract.py`：**24 / 24 断言通过**（A 段 5 + B 段 15 + C 段 4）。

该脚本独立于 pytest 存在，原因是仓库 venv 为 Python 3.9，而宿主
`agent.anthropic_adapter` 使用 PEP 604 需要 ≥ 3.10 ——
若放任 pytest 跳过，`normalize_response` 往返就成了未验证项。
现改为在 Hermes 的 3.11 解释器上实跑，**skip 不作为证据**。
