# Credential Guard 0.4.0 —— 安装与运维指南

面向正式 `worker` Profile 的操作手册。读者无需读源码；每一步给出可复制命令与预期结果。

**你的真实起点（2026-08-06 核实）**

| 项 | 现状 | 目标（0.4.0） |
|---|---|---|
| 插件版本 | `0.2.0` | `0.4.0` |
| 工具 | 仅 `mysql_credential_action` | `http_credential_request` + `credential_process_run` |
| 配置 | 见下文「配置现状」 | 完整单文件 `credential-guard.json`（含 `request` 等字段） |

正式安装包路径（仓库内）：

`dist/credential-guard-0.4.0-hermes-plugin.zip`  
期望 sha256：`1fbc8c38da81226ef8a98f50702f2b3f5b369c5ce4767b8d0de8b2aaad20908d`

下文用 `REPO` 表示本仓库根目录，例如：

```bash
export REPO=/Users/yelei/data/code/repos/hermes-credential-guard
export ZIP="$REPO/dist/credential-guard-0.4.0-hermes-plugin.zip"
export WORKER_HOME="$HOME/.hermes/profiles/worker"
```

## 1. 升级前你需要知道的

1. **跨了两代**：正式 worker 仍是 `0.2.0`；中间的 `0.3.1` 从未在你机器上装过。直接升到 `0.4.0`。
2. **工具形态会变**：旧的 `mysql_credential_action`（以及历史上的四固定动作）会消失；只保留两个通用工具。旧用法不能原样继续。
3. **配置格式已变**：`0.2.0` 时代是双文件 `credentials.json` + `targets.json`；`0.4.0` 只认单文件 `credential-guard.json`。非空旧双文件**不会**被自动改写成可用业务配置（见第 3 节）。
4. **必须重启 worker gateway** 后新插件才生效。
5. **`hermes plugins install` 只接受 Git 地址**，不接受本地 ZIP。本指南用「备份 → 解压替换插件目录」安装本地制品。
6. **Agent 不会替你操作正式 worker**。下列步骤由你本人执行。

### 配置现状（只读核实结论，供你对照）

- 插件目录：`$WORKER_HOME/plugins/credential-guard`（`plugin.yaml` 显示 `version: 0.2.0`）。
- 当前 `hermes -p worker plugins list` 中 `credential-guard` 可能显示 **not enabled**——升级后必须显式启用。
- 配置目录：`$WORKER_HOME/credential-guard/`。
  - 若这里**已有** `credential-guard.json`：跳过「把双文件迁成空壳」的自动迁移，改为按第 5 节补全字段。
  - 若这里仍是 `credentials.json` + `targets.json`：走第 3 节迁移。
- 本轮核实还发现：即便已有单文件，若缺少 HTTP binding 的 `request`（`allowed_methods` / `allowed_paths`），`0.4.0` 会以 `CONFIG_SCHEMA` 拒绝加载——安装前必须按模板补全。

## 2. 备份（可回滚的前提）

**可回滚。请先做完本节再继续。**

```bash
export BACKUP_ROOT="$HOME/backups/cg-pre-0.4.0-$(date +%Y%m%d-%H%M%S)"
mkdir -p "$BACKUP_ROOT"

# 1) 插件目录（0.2.0）
cp -a "$WORKER_HOME/plugins/credential-guard" "$BACKUP_ROOT/plugin-credential-guard-0.2.0"

# 2) 配置目录（单文件或双文件都在这里）
cp -a "$WORKER_HOME/credential-guard" "$BACKUP_ROOT/store-credential-guard"

# 3) 记录版本与哈希，便于核对备份可用
shasum -a 256 "$BACKUP_ROOT/plugin-credential-guard-0.2.0/plugin.yaml" \
  > "$BACKUP_ROOT/plugin.yaml.sha256"
find "$BACKUP_ROOT/store-credential-guard" -type f -exec shasum -a 256 {} \; \
  > "$BACKUP_ROOT/store-files.sha256"

# 4) 核对 ZIP 身份（必须与验收报告一致）
shasum -a 256 "$ZIP"
# 预期仅一行，以 1fbc8c38… 开头、以 …ad20908d 结尾
```

**验证备份可用**

```bash
test -f "$BACKUP_ROOT/plugin-credential-guard-0.2.0/plugin.yaml"
grep -q 'version: 0.2.0' "$BACKUP_ROOT/plugin-credential-guard-0.2.0/plugin.yaml" && echo PLUGIN_BACKUP_OK
test -d "$BACKUP_ROOT/store-credential-guard" && echo STORE_BACKUP_OK
wc -l "$BACKUP_ROOT/store-files.sha256"
```

预期：打印 `PLUGIN_BACKUP_OK`、`STORE_BACKUP_OK`；`store-files.sha256` 至少有一行。

把 `BACKUP_ROOT` 路径记下来——回滚全靠它。

## 3. 旧配置迁移

**术语**：`migrate-config` = 插件提供的一次性命令，把旧双文件读入并尝试写出新单文件；**它不会把旧 MySQL/SSH 目标自动变成新的 HTTP/env/stdin 绑定**。

### 3.1 你是否还需要跑迁移？

```bash
ls -la "$WORKER_HOME/credential-guard"
```

| 目录里有什么 | 怎么做 |
|---|---|
| 仅有 `credentials.json` + `targets.json` | 继续 3.2 |
| 已有 `credential-guard.json` | **不要**再跑会与之冲突的迁移；跳到第 5 节补全/重写单文件 |
| 两者都有 | **停止**，先问；不要继续覆盖 |

### 3.2 用 0.4.0 制品在临时环境跑迁移（推荐；不碰正式目录）

正式 worker 上的 `0.2.0` **没有**可用的 `hermes credential-guard migrate-config`（插件未启用时该子命令甚至不存在）。请用 ZIP 里的 `0.4.0` 代码，在**副本**上跑：

```bash
# 解压 0.4.0 到临时目录
EXTRACT=$(mktemp -d /tmp/cg040-extract-XXXXXX)
unzip -q "$ZIP" -d "$EXTRACT"
PLUGIN_SRC="$EXTRACT/credential-guard"

# 复制旧双文件到 0700 临时店（绝不在正式目录就地迁移）
MIG=$(mktemp -d /tmp/cg040-mig-XXXXXX)
chmod 700 "$MIG"
STORE="$MIG/credential-guard"
mkdir -m 700 "$STORE"
cp -p "$WORKER_HOME/credential-guard/credentials.json" "$STORE/" 2>/dev/null || true
cp -p "$WORKER_HOME/credential-guard/targets.json" "$STORE/" 2>/dev/null || true
chmod 600 "$STORE"/*.json 2>/dev/null || true
ls -la "$STORE"
```

若上面 `ls` 看不到两份 json，说明正式目录并不是双文件形态——停在这里，改走第 5 节。

```bash
# 在副本上调用 0.4.0 的 migrate-config
HERMES_HOME="$MIG" PYTHONPATH="$PLUGIN_SRC" python3 - <<'PY'
from credential_guard.migration import run_migrate_config
raise SystemExit(run_migrate_config())
PY
```

### 3.3 预期输出（两种都正常）

**A. 旧双文件非空（真实业务常见）**

```text
credential-guard: migrate-config failed (MIGRATION_REQUIRES_MANUAL_REVIEW)
```

退出码非 0。  
**这不是故障**——表示：旧内容无法静默映射到新 schema，必须由你按第 5 节**手工写成**新的 `credential-guard.json`。  
副本里的旧双文件应保持原样；正式目录未被修改。

**B. 旧双文件都是空映射（仅测试空壳）**

```text
credential-guard: migrate-config ok
config_digest=<64位十六进制>
```

会生成空的 `credentials` / `bindings`。业务凭证仍需你按第 5 节填写。

### 3.4 人工复核清单（出现 `MIGRATION_REQUIRES_MANUAL_REVIEW` 时）

对照旧双文件的**名字与类型**（不要把密码粘到聊天里），在新单文件中重新表达：

1. 每条旧 credential → 新 `credentials` 里的 `token` 或 `username_password`。
2. 每个要用凭证的目标 → 新 `bindings` 里的 `http` / `process_env` / `stdin` 之一（旧 `mysql` / `ssh_config` **不会**原样保留）。
3. 每个 HTTP binding 必须有 `request.allowed_methods` 与 `request.allowed_paths`。
4. `approval` 固定为 `"required"`。
5. 凭证值只写进本地文件，权限目录 `0700`、文件 `0600`。

复核完成后清理临时目录：

```bash
rm -rf "$EXTRACT" "$MIG"
```

## 5. 启用与配置

### 5.1 启用插件

```bash
hermes -p worker plugins enable credential-guard
hermes -p worker plugins list | grep -i credential-guard
```

预期：`credential-guard` 显示为已启用，版本 `0.4.0`。

若提示需要改 `config.yaml` 里的 `plugins.enabled`：只追加 `credential-guard` 这一项，**不要**改模型、审批模式或其他键。审批模式应保持 `manual`。

### 5.2 单文件模板（凭证值全部为占位符）

路径：`$WORKER_HOME/credential-guard/credential-guard.json`  
目录权限 `0700`，文件权限 `0600`。

下面模板可直接作骨架；把 `REPLACE_*` 换成你的真实值（只写在本地文件，不要贴到聊天）：

```json
{
  "version": 2,
  "credentials": {
    "example_api_token": {
      "type": "token",
      "value": "REPLACE_WITH_TOKEN_VALUE"
    },
    "example_basic_user": {
      "type": "username_password",
      "username": "REPLACE_WITH_USERNAME",
      "password": "REPLACE_WITH_PASSWORD"
    }
  },
  "bindings": {
    "example-http-bearer": {
      "type": "http",
      "credential_ref": "example_api_token",
      "target": {
        "scheme": "https",
        "host": "api.example.test",
        "port": 443
      },
      "request": {
        "allowed_methods": ["GET", "POST"],
        "allowed_paths": ["/v1/health", "/v1/job/build"]
      },
      "inject": {
        "type": "bearer",
        "location": "authorization_header"
      },
      "approval": "required"
    },
    "example-process-env": {
      "type": "process_env",
      "credential_ref": "example_api_token",
      "program": "/usr/bin/false",
      "argv": ["/usr/bin/false"],
      "env_name": "EXAMPLE_TOKEN",
      "timeout_seconds": 30,
      "max_stdout_bytes": 65536,
      "max_stderr_bytes": 65536,
      "approval": "required"
    },
    "example-stdin": {
      "type": "stdin",
      "credential_ref": "example_api_token",
      "program": "/usr/bin/false",
      "argv": ["/usr/bin/false"],
      "stdin_format": "raw",
      "timeout_seconds": 30,
      "max_stdout_bytes": 65536,
      "max_stderr_bytes": 65536,
      "approval": "required"
    }
  }
}
```

字段说明（摘要）：

| 字段 | 含义 |
|---|---|
| `credentials.*.type` | `token` 或 `username_password` |
| `bindings.*.type` | `http` / `process_env` / `stdin` |
| `credential_ref` | 引用上面 credentials 的名字（逻辑代号，不是密码本身） |
| `target` | HTTP 允许的 scheme/host/port |
| `request.allowed_methods` / `allowed_paths` | HTTP 白名单（**必填**；缺了会 `CONFIG_SCHEMA`） |
| `inject` | `bearer` / `basic` / `api_key` 等注入方式 |
| `program` / `argv` / `env_name` / `stdin_format` | 本地固定程序注入参数（由配置决定，不由模型决定） |
| `approval` | 固定 `"required"` |

写好后：

```bash
chmod 700 "$WORKER_HOME/credential-guard"
chmod 600 "$WORKER_HOME/credential-guard/credential-guard.json"
```

### 5.3 重启

```bash
hermes -p worker gateway restart
hermes -p worker gateway status
```

预期：gateway 为 running。

## 6. 验证

在 worker 会话里做一次不伤生产的观察（不要要求模型打印密码）：

**判据 A —— 工具是两个，不是一个**

```bash
hermes -p worker plugins list | grep -i credential-guard
# 预期：version 0.4.0，且为 enabled
```

在实际对话/工具列表中应能看到：

- `http_credential_request`
- `credential_process_run`

不应再看到 `mysql_credential_action`。

**判据 B —— 审批提示里是凭证代号，不是明文**

触发一次需要审批的工具调用后，审批界面应出现逻辑引用/代号（例如 credential 名或 `<CREDENTIAL:…>` 形态），**不应**出现你写进 `credential-guard.json` 的真实 token/password。

**判据 C —— 运维检查（可选）**

```bash
hermes -p worker credential-guard check
```

预期：退出码 0，并报告插件已加载启用、拦截点注册正常。若子命令仍不存在，说明插件未启用或 gateway 未加载新目录——回到 5.1 / 5.3。

## 7. 卸载

**可回滚到“无此插件”，但会失去凭证边界能力。**

```bash
hermes -p worker gateway stop
hermes -p worker plugins disable credential-guard
mv "$WORKER_HOME/plugins/credential-guard" \
   "$WORKER_HOME/plugins/credential-guard.disabled-$(date +%Y%m%d)"
hermes -p worker gateway start
```

配置目录 `$WORKER_HOME/credential-guard/` **默认保留**（避免误删钥匙）。若你确定要删除配置，只能你自己删，并且必须先有第 2 节备份。

## 8. 回滚到 0.2.0

**什么情况下回滚**：新插件无法启用、工具列表不对、配置反复 `CONFIG_SCHEMA`、或业务临时必须回到旧 `mysql_credential_action`。

```bash
# BACKUP_ROOT 用第 2 节记下的路径
hermes -p worker gateway stop

# 换回 0.2.0 插件目录
rm -rf "$WORKER_HOME/plugins/credential-guard"
cp -a "$BACKUP_ROOT/plugin-credential-guard-0.2.0" \
      "$WORKER_HOME/plugins/credential-guard"

# 配置：若 0.4.0 改坏了单文件，从备份整目录恢复
# （会覆盖当前 store；确认后再执行）
rm -rf "$WORKER_HOME/credential-guard"
cp -a "$BACKUP_ROOT/store-credential-guard" "$WORKER_HOME/credential-guard"

hermes -p worker plugins enable credential-guard
hermes -p worker gateway start

grep -q 'version: 0.2.0' "$WORKER_HOME/plugins/credential-guard/plugin.yaml" \
  && echo ROLLBACK_PLUGIN_OK
```

**回滚后配置怎么处理**

- 若你已开始按新 schema 重写单文件：回滚插件后，旧 `0.2.0` **不一定**能理解新单文件；优先恢复备份中的 store。
- 若备份 store 仍是双文件：保持双文件，供 `0.2.0` 使用。
- 不要把 `0.4.0` 的半成品单文件与 `0.2.0` 混用而不核对。

## 9. 停止条件（别继续，先问）

出现以下任一情况时**停手**，保留现场与 `BACKUP_ROOT`，再问：

1. ZIP 的 sha256 不是 `1fbc8c38…ad20908d`。
2. 正式目录里双文件与单文件同时存在，不知该留哪个。
3. `migrate-config` 返回除 `MIGRATION_REQUIRES_MANUAL_REVIEW` 以外的错误码（例如 `MIGRATION_SOURCE_SCHEMA`、`MIGRATION_TARGET_EXISTS`、`MIGRATION_DIR_INSECURE_MODE`）。
4. 启用后 `plugin.yaml` 不是 `0.4.0`，或工具列表仍只有 `mysql_credential_action`。
5. 审批提示或日志里出现了真实密码/token。
6. gateway 无法启动，或 `config.yaml` 被误改到模型/审批模式异常。
7. 任何步骤要求你读取或粘贴 `~/.ssh` 或真实业务密码到聊天。
