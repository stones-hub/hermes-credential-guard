## 1. 与最终目标对齐

项目终局不变：**让模型能指挥工作，但永远拿不到真实凭证。**

R3 只完成最终目标中的 STEP 5：**人工审批通过并完成 R2 最终复核后，本机临时解析并注入本次批准的真实凭证，执行一次受控调用。**

R3 不改变最终目标的下列原则：

1. 模型只知道业务目标、结构化请求和 `<CREDENTIAL:name>`，永远拿不到真实密码、Token 或私钥；
2. 每次真实凭证使用复用 Hermes 标准 manual 审批，不实现第二套审批；
3. R2 已绑定的工具、参数位置、目标、配置摘要和调用身份不可偷换、不可跨调用复用；
4. 真值只在可信本机、批准的协议和批准的位置短暂出现；
5. 不在任意 SQL、Shell、聊天或普通字符串中全局还原引用；
6. 新增 Jenkins、内部 API 或 CLI 目标原则上只改 `credential-guard.json`，不新增业务专用动作；
7. 普通编码、文件、Git、terminal、SSH Config、Docker/systemd 和日志排障不受影响；
8. 任一验证、解析、注入或执行环节异常都 fail closed；
9. R3 只建立安全注入与一次受控执行；完整结果守卫和非干扰矩阵仍由 R4 收口，但 R3 自身不得主动把真值放入返回值、日志或异常。

## 2. R3 做完后用户能得到什么

### 2.1 HTTP / Jenkins / 内部 API

模型提交业务目标、method、相对 path、query/body 与逻辑 credential；用户批准后，本机依据 binding 中不可见于模型的 scheme/host/port/auth 规则组装一次结构化 HTTP 请求，把真值只注入指定 Header。

第一版支持：

- Bearer Token；
- Basic Auth；
- 自定义 API-Key Header；
- HTTPS 精确 scheme/host/port；
- 配置允许范围内的 method 与相对 path；
- 有界 query/body；
- 默认拒绝所有重定向。

### 2.2 需要环境变量的本地 CLI

模型只选择配置登记的逻辑 target，并提交受限结构化 argv；用户批准后，本机用绝对路径启动一次配置登记的本地程序，把真值加入这一个子进程的独立 env 副本。

真值不写入：

- `os.environ`；
- command 字符串；
- argv；
- shell history；
- 审批、trace 或模型上下文。

### 2.3 支持 stdin 的本地 CLI

模型仍只能选择配置登记的固定程序和受限 argv。批准后，真值只写入该程序明确支持的 stdin；不拼入 command/argv，不回退成环境变量或自由 Shell 字符串。

## 3. 范围与停止点

### R3 实现

- 审批后单凭证按需解析；
- 一次执行上下文；
- 结构化 HTTP Header 注入；
- 固定本地程序的单次 env 注入；
- 固定本地程序的 stdin 注入；
- 真实主 Agent 路径 E2E；
- 拒绝、超时、重放、配置/参数偷换、解析/执行异常 fail closed；
- 合成凭证 + loopback 假目标验收。

### R3 不实现

- 任意 Shell 字符串替换；
- `sh -c`、`bash -c`、`zsh -c` 或同类二次解释入口；
- 任意 SQL、任意 SSH 命令、任意 argv 凭证注入；
- 将真值放进 query/body、普通 argv 或文件；
- OAuth 自动刷新、AWS SigV4、mTLS、特殊签名算法；
- 真实 Jenkins/GitLab/API/数据库/服务器连接；
- 修改 Hermes 源码；
- 正式 worker 安装、启用、配置或升级；
- 覆盖 0.3.1 历史制品；
- R4 完整结果守卫、R5 旧架构删除、R6 发布构建。

## 4. 总体执行链

### 4.1 引用路径

```text
模型提交结构化请求 + <CREDENTIAL:name>
→ R2 tool_request 建立 InjectionPlan
→ R2 pre_tool_call 展示安全审批摘要
→ Hermes manual 审批
→ R2/R3 handler 在共享配置锁内最终复核
→ 原子消费一次性 plan
→ 仅解析该 plan 所需的一个 credential
→ 按 binding 选择 HTTP / process_env / stdin 适配器
→ 构造仅存在于本次执行上下文的参数副本
→ 执行一次
→ 清理本次上下文
→ 返回不主动包含真值的结构化结果
→ R4 后续统一结果守卫再做完整回流收口
```

### 4.2 普通无引用路径

普通无引用工具不创建 plan、不解析 credential、不进入注入适配器，保持原工具 `next_call` 恰好一次、参数和结果语义不变。

## 5. 注入内核设计

### 5.1 复用 R2，不建第二条执行链

R3 不再新增一个并列 `tool_execution` middleware。现有 R2 `tool_execution → pre_tool_call/approval → 正式 handler` 是唯一主链：

- middleware 继续负责把正式调用窗口和 identity 绑定给 handler；
- handler 继续负责最终 lstat、config/binding/target/args/identity 复核；
- 原先固定返回 `RUNTIME_ADAPTER_NOT_READY` 的位置，改为调用 R3 注入内核；
- compatibility dispatcher 保留兼容测试，但不能冒充主 Agent 验收。

### 5.2 消费、解析和执行顺序

顺序固定为：

1. 在现有共享 config lock + execution recheck lock 内读取当前安全视图并复核；
2. 原子消费 `APPROVAL_PENDING` plan；
3. 根据已消费 plan 的 credential name，从当前已验证配置中仅解析这一份真值；
4. 立即创建不支持 repr/序列化的本地执行上下文；
5. 选择配置声明的唯一 adapter 并执行一次；
6. `finally` 中清理引用和临时缓冲；
7. 任何异常返回固定安全错误，不再调用其他 adapter 或 fallback。

说明：plan 必须先一次性消费再执行，避免网络/子进程副作用后仍保留可重放 plan；解析失败或执行失败也不能复用原审批。

### 5.3 SecretResolver 最小接口

建议新增 `credential_guard/injection.py`，只暴露内部接口：

```python
resolve_one_for_execution(consumed_plan, verified_view) -> SecretLease
execute_with_adapter(consumed_plan, safe_args, secret_lease) -> SafeAdapterResult
```

`SecretLease` 约束：

- 只持有本次一个 credential；
- 禁止 `repr`、JSON、pickle、copy/deepcopy；
- 不写日志、trace、异常正文；
- 只允许 adapter 在执行函数内读取；
- 执行完成后在 `finally` 释放引用；
- 不宣称 Python `str/bytes` 可物理擦除，诚实限定为最短生命周期和不可外发。

## 6. 配置模型补充

R3 延续单一 `credential-guard.json`，不新建第二份目标文件。binding 仍是 target、credential、工具、参数位置、注入方式和审批要求的唯一规则。

### 6.1 HTTP binding

> **实施修正（0.4.4 核对）**：本节示例原含 `allowed_tools` / `reference_arg_path` 两个字段，以及 `allowed_path_patterns` 字段名。这三者均**不在实际 schema 白名单内**，照抄会导致整个配置文件被拒、插件全线 fail-closed。已按实现修正。
>
> HTTP binding 顶层白名单（`bindings.py:_HTTP_FIELDS`）仅六键：`type`、`credential_ref`、`target`、`request`、`inject`、`approval`。
> `allowed_tools` 与 `reference_arg_path` 由 `runtime_config.py` 按 binding 类型自动推导，**永远不应出现在用户配置中**。

```json
{
  "type": "http",
  "credential_ref": "jenkins-token",
  "target": {
    "scheme": "https",
    "host": "jenkins.example.test",
    "port": 443
  },
  "request": {
    "allowed_methods": ["POST"],
    "allowed_paths": ["/job/project-x/build"],
    "connect_timeout_seconds": 5,
    "total_timeout_seconds": 30,
    "max_response_body_bytes": 65536
  },
  "inject": {
    "type": "bearer",
    "location": "authorization_header"
  },
  "approval": "required"
}
```

字段说明：

- `target` 仅接受 `scheme` / `host` / `port` 三键；
- `request` 必填 `allowed_methods`、`allowed_paths`（**注意是 `allowed_paths`，不是 `allowed_path_patterns`**），可选三个上限/超时键；
- `inject.type` 为 `bearer` / `basic` / `api_key_header`，其中 `api_key_header` 用 `header_name` 而非 `location`。

约束：

- `host` 只在本地配置中，审批和模型安全摘要只显示业务 target；
- path 第一版使用精确值或有界、可证明的 segment pattern，不接受任意 regex；
- auth header 名由 adapter/配置共同约束，禁止 `Host`、`Content-Length`、hop-by-hop header 和换行；
- query/body 不能出现 credential 引用或真值；
- 配置摘要纳入全部 R3 新字段，配置变化使旧审批失效。

### 6.2 Process binding

> **实施修正（0.4.4 核对）**：本节示例原采用嵌套 `process` 对象 + `argv_template` + `allowed_fields` + 嵌套 `inject` 的形态，与实际实现**完全不同**。实际 schema 为扁平结构，且不支持模型填充 argv 字段。已按实现修正。

`process_env` 顶层白名单（`bindings.py:_PROCESS_ENV_FIELDS`）：`type`、`credential_ref`、`program`、`argv`、`env_name`、`timeout_seconds`、`max_stdout_bytes`、`max_stderr_bytes`、`approval`。

```json
{
  "type": "process_env",
  "credential_ref": "internal-cli-token",
  "program": "/opt/company/bin/internal-cli",
  "argv": ["/opt/company/bin/internal-cli", "--check"],
  "env_name": "INTERNAL_API_TOKEN",
  "timeout_seconds": 30,
  "max_stdout_bytes": 65536,
  "max_stderr_bytes": 65536,
  "approval": "required"
}
```

stdin binding 把 `type` 改为 `stdin`，用 `stdin_format` 取代 `env_name`（`raw` 不追加换行，`line` 追加单个换行）：

```json
{
  "type": "stdin",
  "credential_ref": "internal-cli-token",
  "program": "/opt/company/bin/internal-cli",
  "argv": ["/opt/company/bin/internal-cli", "--stdin"],
  "stdin_format": "line",
  "timeout_seconds": 30,
  "max_stdout_bytes": 65536,
  "max_stderr_bytes": 65536,
  "approval": "required"
}
```

**argv 是完全固定的**：`argv[0]` 必须等于 `program`，且不接受任何模型填充的占位字段。原方案设想的 `argv_template` + `allowed_fields` 未实现——模型无法影响命令行的任何部分，只能决定「是否发起这次调用」。

约束：

- executable 必须绝对路径、普通文件、非 symlink、当前可信 owner、不可 group/world writable；
- 禁止所有 shell executable/interpreter 及 `-c`/`--command` 等二次解释模式；
- 禁止任意 env 名；禁止 PATH、HOME、HERMES_HOME、PYTHONPATH、LD_*/DYLD_*、SHELL、BASH_ENV、ENV 等控制执行环境的变量；
- 子进程 env 基于最小安全 allowlist，不直接复制全部 `os.environ`；
- stdin 模式不允许同时 env 注入；
- 不支持一种注入方式时 fail closed，不自动降级到另一种方式。

## 7. HTTP 适配器边界

### 7.1 请求构造

- URL 只由本地 binding 的 scheme/host/port + 模型提交的相对 path 组成；
- 模型不能提交完整 URL、host、port、userinfo 或 Authorization；
- 只允许 HTTPS；loopback 测试可通过测试专用依赖注入提供假 transport，不放宽生产 Schema；
- method 必须属于 binding allowlist；
- path 必须以 `/` 开头，拒绝 `//`、反斜杠、控制字符、dot segment、编码后 dot segment 和 authority 混淆；
- query/body 大小、层级、键数量有界；
- Header 名和值禁止 CR/LF/NUL；
- 凭证只能进入 binding 指定的 Header。

### 7.2 DNS、连接与重定向

第一版采用最简且边界清晰的策略：

- 精确 host/port；
- 默认 `redirect = false`，3xx 返回安全结果但不跟随；
- 禁止代理环境变量影响连接；
- 明确连接超时与总时长墙钟上限（`connect_timeout_seconds` / `total_timeout_seconds`）；响应 body 有上限；
- 不宣称 urllib 解析期的响应 Header 字节上限（标准库在 `open()` 返回前已解析 headers）；返回给模型的 Header 仅经安全 allowlist/序列化有界；
- 生产 transport 不接受调用参数覆盖 TLS 校验、SNI、Host 或 resolver；
- 测试以 loopback 假 transport/本地假服务验证，不连接外网。

R3 不宣称解决 DNS rebinding 的所有 OS 级问题；但同一次请求中用于校验和连接的目标必须来自同一已验证 binding，不能由模型第二次解释。

### 7.3 返回结果

R3 只返回有界结构化结果，例如：

```json
{
  "ok": true,
  "status": 201,
  "headers": {"content-type": "application/json"},
  "body": {"queued": true},
  "truncated": false
}
```

- 默认只返回安全 Header allowlist；不回传 Authorization、Set-Cookie、Proxy-Authenticate 等敏感 Header；
- body 按上限读取，超限截断并标记；
- adapter 异常返回固定错误码，不返回 URL、host、凭证、原始异常或本地路径；
- R3 测试必须证明 adapter 本身不主动返回真值；完整编码变体/异常/回流门禁由 R4 再统一覆盖。

## 8. Process env / stdin 适配器边界

### 8.1 执行模型

R3 新增一个正式的结构化本地执行工具（建议名：`credential_process_run`），而不是复用任意 `terminal.command` 字符串：

模型可提交：

```json
{
  "target": "internal-cli-deploy",
  "credential": "<CREDENTIAL:internal-cli-token>",
  "params": {"project": "project-x"}
}
```

模型不可提交：

- executable；
- command 字符串；
- env；
- stdin；
- cwd；
- shell 开关；
- 任意 argv 数组。

### 8.2 子进程安全

- 直接 `subprocess.run(argv, shell=False, env=safe_env, input=...)`；
- 不继承危险环境变量；
- 固定或配置允许的 cwd；
- 文件描述符关闭；
- timeout 后终止并等待，不留孤儿进程；
- stdout/stderr 分别有界读取；
- 凭证不得出现在 argv、进程标题、日志或异常；
- 返回前做最小即时 scrub，R4 再接统一结果守卫；
- 目标程序若把真值主动打印出来，R3 必须保证当前结果不直接泄漏；R4 负责把该能力扩展为统一、可验证、覆盖编码变体的最终守卫。

## 9. 分阶段交付

### R3A：注入内核 + HTTP 完整闭环

目标：完成最有业务价值、边界最清晰的审批后执行。

产出：

- `credential_guard/injection.py`；
- `credential_guard/adapters/http.py`；
- 现有 `http_credential_request` 正式 handler 从 `RUNTIME_ADAPTER_NOT_READY` 切换到 HTTP adapter；
- HTTP binding Schema；
- 合成凭证 + loopback fake transport/service；
- 真实主 Agent approve/deny/mutate/replay E2E。

验收：

- approve：approval=1、resolve=1、adapter=1、fake target=1；
- deny/timeout：resolve=0、adapter=0、target=0；
- config/args/identity mutate：resolve=0、adapter=0；
- replay：第二次 adapter=0；
- Provider/approval/trace 真值计数=0；
- redirect/host/path/header/size/timeout 反例全部阻断；
- 普通无引用工具不受影响。

### R3B：固定本地程序 env + stdin

目标：支持配置登记的 CLI，而不开放万能 Shell。

产出：

- `credential_guard/adapters/process_env.py`；
- `credential_guard/adapters/stdin.py`；
- `credential_process_run` 正式结构化工具与 handler；
- process binding Schema；
- 合成 helper 程序，仅返回安全观测值，不回显真值。

验收：

- env：子进程内可见恰好一次，父进程和后续子进程不可见；
- stdin：helper 收到恰好一次，argv/env 真值计数=0；
- deny/timeout/mutate/replay：process start=0；
- executable/symlink/mode/owner/argv/env-name/timeout/output-limit 反例阻断；
- shell、解释器、`-c`、管道、重定向、任意 argv 不可表达；
- adapter 不支持时不降级。

### R3C：主 Agent E2E、全量回归与冻结复审

目标：证明三个适配器均沿真实 Hermes 主循环工作，且没有把 R2 证据改回假绿。

验收：

- 使用 PluginManager 已注册生产 callback/handler，不覆盖 callback list，不包装重注册；
- `sys.setprofile` 或等价非侵入观测真实顺序；
- Provider wire、审批、trace、tool result 真值为 0；
- R0–R2 全部回归；
- R3 专项和 mutation 全绿；
- 全量 pytest 0 failed、compileall 通过；
- 候选外固定算法冻结两次一致；
- Cursor + 两路 Hermes 最终只读复审均 PASS；
- 只在签收后更新 CLAUDE.md、HANDOVER.md、实施计划和 R3 实测报告。

## 12. 需要用户确认的方案决策

本方案给出明确推荐，用户只需确认是否同意：

1. **同意 R3 分为 R3A HTTP、R3B env/stdin、R3C 总验收三个交付单元。**
2. **同意 env/stdin 只服务配置登记的固定本地程序，新增正式结构化工具 `credential_process_run`；不向任意 `terminal.command` 注入。**
3. **同意 HTTP 第一版只允许 HTTPS 精确目标且完全禁止重定向。**
4. **同意 R3 adapter 先做最小即时结果 scrub，完整统一结果守卫仍由 R4 收口，但任何诱饵真值回流都视为 R3 blocker。**
5. **同意 R3 继续只用合成凭证和 loopback 假目标，不连接正式系统、不升级 worker。**
