# Credential Guard 0.4.5 Release Notes

## Breaking changes

0.4.5 is the **first formally released version** (0.3.1 / 0.4.0 / 0.4.4 were built
but never tagged and never published as GitHub Releases). Two behaviours changed
relative to those internal builds:

- **No configuration means fail-closed, not pass-through.** If the plugin is
  enabled and no usable credential store is found, chat is **blocked** with a
  local diagnostic naming the expected config path. Create the config first; see
  README. (This reverses the C1 "zero-config pass-through" behaviour that earlier
  0.4.5 drafts described — see *Withdrawn* below.)
- **The v1 dual-file migrator is gone.** `credential_guard/migration.py` and the
  `migrate-config` subcommand were removed. There is no automatic migration from
  v1 (`credentials.json` + `targets.json`) to the v2 single file. A v1 config
  must be rebuilt by hand per README. This affects no existing user, because no
  prior version was ever released.

## Withdrawn

- **C1 zero-config pass-through — withdrawn by design decision.** Earlier 0.4.5
  drafts let a machine with no store chat normally. That was reversed: an
  unconfigured plugin now fails closed. The counter-case is unchanged — an
  existing but corrupt store has always failed closed (Provider=0).

## Highlights

R11 is an **out-of-box usability and protection-boundary transparency** release.
0.4.4 hardened what the plugin blocks; 0.4.5 makes sure a plain user who
installs the plugin can tell what it is protecting and why it refused.

- **Store location derived from the install path.** The plugin no longer guesses
  its configuration directory from the `HERMES_HOME` environment variable. It
  derives the profile root from its own installed location
  (`credential_guard/store_location.py` is the single source of truth), so a
  per-profile install gets a per-profile config. Verified constant across
  `HERMES_HOME` unset / pointing elsewhere / empty.
- **Field-level configuration diagnostics (C2)** — configuration failures report
  a whitelisted structured `location` plus a fixed remediation line, locally
  only. Illegal / over-long / control-character locations degrade to the fixed
  `configuration` value.
- **Safe target catalog sidecar (C5)** — `credential-guard.targets.json` carries
  only declarative, non-secret metadata and is read-only at registration time.
  It is **not** an execution authorization source; `credential-guard.json`
  remains the only file that may contain a secret.
- **Fixed refusal for redacted-code misuse (C6)** — passing a redacted display
  code such as `<SECRET:cg_…>` back in as if it were a credential reference now
  returns the fixed `CREDENTIAL_CODE_NOT_USABLE` error instead of a confusing
  generic failure.
- **Local unregistered-credential reminder (C7)** — a bounded, local-only
  reminder when material looks like an unregistered secret. This is a reminder,
  not DLP, and it is explicitly not a coverage claim.
- **Offline `validate` (C10)** — `hermes credential-guard validate [file]`
  checks a Schema v2 config with no network, no Provider call, no adapter, and
  no sidecar generation. Output is PASS/FAIL lines with fixed codes and safe
  locations only.

## Fixes

- **C8 — dead error code removed.** `RUNTIME_ADAPTER_NOT_READY` was returned
  from every reference-path exit, including paths that had nothing to do with an
  unready adapter, so the message actively misled diagnosis. Exits now carry
  their real cause: `REFERENCE_PATH_BLOCKED`, `CALL_IDENTITY_REQUIRED`,
  `PLAN_NOT_FOUND`, `PLAN_NOT_PENDING`, `PLAN_RECHECK_FAILED`.
- **C9 — placeholder unification.** Redacted display values use one shape,
  `<SECRET:cg_[0-9a-f]{16}>`. Tool arguments keep `<CREDENTIAL:name>`; the two
  are deliberately distinct and misuse of the former is refused (see C6).
- **Non-interference under permanent back-pressure.** Hot-path local event
  logging moved to a bounded async queue, so a blocked stderr can no longer
  stall a Provider call.
- **Build script no longer deletes released artifacts.**
  `clean_prior_artifacts()` used version-agnostic globs (`*.whl`, `*.tar.gz`,
  `*-hermes-plugin.zip`). Building directly into the repository `dist/` would
  silently delete every previously released artifact — measured on a copy:
  `dist/` went from 12 files to 7, and four hash-freeze gates went red. Cleanup
  is now version-scoped: only the current version's four formal filenames and
  their `-0.4.5-` anchored `.tmp` leftovers are removed. Two load-bearing
  regressions were added and verified with two-way mutation.

## Security invariants (unchanged)

- Real secrets stay in the local protected store; credentials never travel
  through the conversation.
- Manual approval is still required before any local credential injection.
- Plaintext credentials are never read before approval.
- Synthetic / decoy values only, in tests and examples.
- `<SECRET:…>` display codes are not usable as references.

## Known boundary (unchanged, stated plainly)

Credential Guard is a plugin. It protects the Hermes main chat conversation
loop and main-chain tool results. It does **not** cover auxiliary model calls
(title generation, context compression, vision, oneshot, `session_search`), and
it does **not** perform generic secret detection for credentials you never
registered. See "当前边界" in `README.md`.
