# R9 / 0.4.3 长 Session 连续性修复方案

## 大白话

长会话里，模型请求会越积越大。Credential Guard 只应在「无法证明已清理干净」时阻断，并把原因说清楚；能安全替换或隔离的历史字段应替换后继续，而不是逼用户新建 Session。

0.4.3 把今天已落地的长 Session 连续性能力收成正式发布候选，并补上一项终审观察项的窄修：协议骨架字段（如 `model` / `role` / `name` / `tool_call_id`）若出现不可精确定位的编码私钥，必须本地 fail-closed（Provider=0），不能整字段换成占位符后再发给 Provider。

## 问题

1. **累计大请求**：多个安全字段合计超过单字段扫描预算时，不应因「整请求再扫一遍」而误阻断。
2. **边界未知编码私钥**：能定位完整边界的替换后继续；无法定位时，内容类字段可整字段占位后继续，协议骨架字段不得继续。
3. **动态键碰撞**：普通动态 key 脱敏后撞名时，分配互不冲突的安全 key，会话继续。
4. **历史残留 / 扫描器边界**：历史可隔离则隔离后继续；当前输入、system、协议骨架等不可隔离则 Provider=0，并给出可操作提示。
5. **当前最后 user 语义**：以「最后一条 `role=user`」为准（其后可有 trailing assistant/tool），不是数组末尾。

## 设计要点

| 主题 | 行为 |
| --- | --- |
| 累计大请求 | 逐字段扫描；禁止用整请求 `json.dumps` 二次触发单串预算 |
| 边界未知整字段替换 | 仅 `messages[*].content` 与 `tool_calls[*].function.arguments` |
| 协议字段 | `model` / `role` / `name` / `tool_call_id` 等 → Provider=0 |
| 动态键碰撞 | 唯一 `<REDACTED_SENSITIVE_KEY_N>`，不派生自原文哈希 |
| residual recovery | 历史 content / arguments 可隔离；当前 user / core 不吞 |
| scanner recovery | 独立封闭 allowlist；**不得**复用到整字段 fallback，也不得放宽当前输入 |
| 仅 Provider-bound 副本 | 永不改写 canonical Session；同一 Session 可直接「继续」 |
| Provider=0 | 配置不可用、碰撞无法安全继续、当前输入残留/扫描失败、协议字段边界未知、预算耗尽等 |

## 安全边界

- 可信：本机 Hermes、标准审批、Credential Guard、本地 `credential-guard.json`、本地执行器
- 不可信：外部模型、供应商、模型参数、Provider 返回
- 不修改 Hermes 源码；不宣称覆盖 `auxiliary_client.call_llm`
- 开发和验收只用合成诱饵、临时 HOME/HERMES_HOME、loopback；不触碰正式 worker / 真实 `~/.ssh`

## 非目标

- 不新增第二套审批票据或 OS 级 DLP
- 不把整字段 fallback 扩到协议骨架或未批准字段
- 不覆盖否决的「统一拦截全部模型外发」方案
