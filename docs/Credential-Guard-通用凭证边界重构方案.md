# Credential Guard 通用凭证边界重构方案

> 状态：R0–R4 已完成并签收；R5 只读盘点、落地方案和严格 TDD 计划已完成，待用户批准删除范围后实施。
>
> 基线：0.3.1 已完成安全收口并冻结。本方案作为后续版本重构，不覆盖 0.3.1 制品，不升级 worker。

## 1. 为什么重构

0.3.1 已证明两件事：

1. 已登记凭证可以在发送给外部模型前被脱敏或阻断；
2. 本机可在人工审批后使用真实凭证执行固定操作。

但当前第二项依赖四个写死动作：

- MySQL：`check_connection`、`show_effective_grants`
- SSH：`check_connection`、`show_remote_identity`

这种模式不适合作为长期产品方向。每增加 Jenkins、内部 API、数据库查询或新的运维操作，都要修改插件、增加动作、重新发版。

本轮将 Credential Guard 从“固定动作执行器”重构为“通用本地凭证边界”。

## 2. 重构目标

插件只负责三件事：

1. **外发脱敏：**真实凭证不进入外部模型请求；模型只看到稳定的逻辑引用。
2. **审批后注入：**模型生成的工具参数经过目标校验和人工审批后，在本机执行边界注入真实凭证。
3. **结果脱敏：**工具结果、错误信息再次检查，真实凭证不回流模型。

插件不再以不断增加业务动作作为扩展方式。

## 3. 不变的边界

- 外部模型和 Provider 不可信。
- 本机 Hermes、Credential Guard、标准人工审批和本机执行环境可信。
- 真实凭证只存在于本机可信配置和短生命周期执行参数中。
- `approvals.mode: manual` 继续使用，不新建第二套审批系统。
- 外发保护、注入解析或结果脱敏任一步失败，都 fail closed。
- 本地日志/state DB/WAL 明文仍为已接受残余，本轮不扩展为 OS 级零明文平台。
- 不读取真实业务凭证、真实 `~/.ssh`，不连接真实服务器或生产数据库进行开发测试。

## 4. 总体架构

| 阶段 | 模型能看到什么 | Credential Guard 做什么 | 真实凭证状态 |
|---|---|---|---|
| 模型请求前 | 业务名称、普通上下文 | 将已登记真实值及编码变体替换为逻辑引用 | 只在本机 |
| 模型生成工具调用 | 工具名、普通参数、逻辑引用 | 校验引用格式，不在此时解析真值 | 只在本机 |
| 人工审批 | 原始工具参数、逻辑引用、凭证别名、允许目标 | 要求单次审批；不显示真值 | 尚未注入 |
| 本机执行前 | 模型不再参与 | 校验工具、参数位置、目标绑定和配置版本；注入真值 | 仅本次执行 |
| 工具执行后 | 安全结果 | 再次脱敏；发现残余即阻断 | 不回流模型 |

推荐默认审批展示：占位符 + 凭证别名 + 允许目标，不显示真实值。用户未在确认时限内另选，方案按此默认编写。

## 5. 单文件配置模型

将 `credentials.json` 和 `targets.json` 合并为：

```text
credential-guard.json
```

合并的是物理文件，逻辑上仍分两部分：

```text
credentials = 有哪些本地钥匙
bindings    = 每把钥匙允许在哪些工具、参数位置和目标中使用
```

建议 Schema：

```json
{
  "version": 2,
  "credentials": {
    "internal_api_token": {
      "kind": "token",
      "value": "[REDACTED]"
    },
    "reporting_mysql": {
      "kind": "username_password",
      "username": "readonly_user",
      "password": "[REDACTED]"
    }
  },
  "bindings": {
    "internal-api": {
      "credential_ref": "internal_api_token",
      "tool": "terminal",
      "placements": [
        {
          "arg": "command",
          "placeholder": "<CREDENTIAL:internal_api_token>",
          "context": "http_authorization_bearer"
        }
      ],
      "target": {
        "scheme": "https",
        "hosts": ["api.example.com"],
        "ports": [443]
      },
      "approval": "required"
    },
    "jenkins-production": {
      "credential_ref": "jenkins_token",
      "tool": "terminal",
      "placements": [
        {
          "arg": "command",
          "placeholder": "<CREDENTIAL:jenkins_token>",
          "context": "http_authorization_basic"
        }
      ],
      "target": {
        "scheme": "https",
        "hosts": ["jenkins.example.com"],
        "ports": [443]
      },
      "approval": "required"
    }
  }
}
```

字段含义：

| 字段 | 含义 |
|---|---|
| `credentials` | 真实凭证，模型不能读取 |
| `bindings` | 凭证引用允许出现的位置和目标范围 |
| `credential_ref` | 绑定使用哪一份凭证 |
| `tool` | 允许在哪个 Hermes 工具中注入 |
| `arg` | 允许注入到工具的哪个参数 |
| `placeholder` | 模型使用的稳定逻辑引用 |
| `context` | 注入语义，如 Bearer Header、Basic Auth、环境变量或 stdin |
| `target` | 凭证允许到达的协议、主机和端口 |
| `approval` | 第一版固定 `required` |

### 5.1 文件安全要求

- 目录 `0700`，文件 `0600`；
- 必须是当前用户拥有的普通文件；
- 禁止符号链接、未知字段、重复引用和悬空引用；
- 整个文件属于敏感路径，普通模型文件工具、terminal 和 execute_code 不得读取或外发；
- 插件可向模型暴露安全摘要，但不得暴露真实 host、credential_ref、凭证值或本地路径。

## 6. 逻辑引用规则

第一版只接受显式、完整、可解析的引用：

```text
<CREDENTIAL:internal_api_token>
```

规则：

- 引用只能由 Credential Guard 根据本地配置生成，不能使用脱敏器的随机 token 反向猜测；
- 未登记、格式错误、重复或嵌套引用直接阻断；
- 一个工具调用可引用多个不同凭证，但每个都必须独立绑定和校验；
- 普通聊天正文中的引用不还原；
- 工具结果中的引用不还原；
- 只有工具调用参数进入可信本地执行阶段时才允许解析。

## 7. 工具参数注入流程

### 7.1 tool_request：只识别，不注入

模型产生工具调用后，Credential Guard 在 `tool_request` 中：

1. 扫描结构化工具参数；
2. 找出逻辑引用；
3. 验证该引用允许用于当前工具和参数；
4. 解析目标信息并验证绑定范围；
5. 生成不含真值的审批摘要；
6. 保持参数中的逻辑引用不变。

此阶段不得读取并注入执行真值。

### 7.2 pre_tool_call：要求审批

只要工具参数含逻辑引用，就要求 Hermes 标准人工审批。

审批页显示：

- 工具名；
- 模型生成的原始参数；
- 凭证别名；
- 允许目标；
- 注入语义；
- 配置版本摘要。

审批页不显示：

- 真实用户名、密码或 Token；
- 完整连接串；
- 替换后的执行参数。

审批拒绝、超时或异常：

- 不解析真实凭证；
- 不执行工具；
- 不产生目标系统副作用。

### 7.3 tool_execution：校验后注入

审批通过后，Credential Guard 在 `tool_execution` 中：

1. 重新加载并严格校验当前配置；
2. 检查配置摘要与审批时一致，防止 TOCTOU；
3. 重新验证工具、参数位置和目标；
4. 仅解析本次引用需要的凭证；
5. 在内存副本中注入；
6. 调用原工具；
7. 执行后立即丢弃副本和引用上下文。

如果配置在审批后变化、目标不一致或解析失败，直接阻断并要求重新发起工具调用和审批。

## 8. 注入方式

第一版按优先级支持：

| 注入方式 | 用途 | 第一版 |
|---|---|---:|
| 结构化 HTTP Header | Bearer、Basic、API-Key | 支持 |
| 子进程环境变量 | CLI 已支持从环境变量读取凭证 | 支持 |
| stdin | CLI 支持从标准输入读取凭证 | 支持 |
| 普通 argv 字段 | 非 shell 工具的独立参数 | 有条件支持 |
| 自由 Shell 字符串替换 | 任意 terminal command | 不直接支持 |

### 8.1 为什么不在任意 Shell 字符串中盲替换

即使审批后替换，真值仍可能进入：

- `ps` 进程参数；
- Shell tracing；
- 命令历史或错误信息；
- 重定向、管道和命令替换；
- 与审批内容不同的二次解释结果。

因此 `terminal.command` 第一版只允许两种安全用法：

1. 模型调用配置中登记的本地 wrapper，凭证通过环境变量或 stdin 注入；
2. 插件能确定性解析并证明目标绑定的 HTTP 请求，随后由本地结构化执行适配层执行，而不是把真值拼回 shell。

普通 SSH 部署继续使用本机 SSH Config 和私钥，不需要凭证回填。

## 9. 对 Hermes 现有使用方式的影响

### 9.1 不受影响

- 本地编码、文件修改、测试、构建；
- Cursor/Claude Code 委派；
- Git 操作；
- 使用 SSH alias 的远端部署；
- Docker、systemd、Nginx 运维；
- 日志查看和 Bug 排查。

### 9.2 新增能力

- 模型可生成包含逻辑凭证引用的结构化工具参数；
- 审批后由本机注入真实 Token、用户名或密码；
- 新增目标和凭证主要改配置，不为每个业务动作改插件；
- 同一凭证可绑定多个明确目标，轮换时只改一处。

### 9.3 仍会阻断

- 模型读取或打印统一配置文件；
- 将凭证引用发送到未绑定目标；
- 在普通聊天正文中要求还原引用；
- 任意 Shell 中无法证明目标和注入位置的盲替换；
- 审批后配置发生变化；
- 插件、配置、脱敏或结果检查异常。

## 10. 旧架构清理要求

0.3.1 的四个动作不再是新架构的扩展模型。

清理策略：

1. 0.3.1 制品保持冻结，不覆盖；
2. 重构开发期暂时保留四个动作作为回归基线；
3. 通用注入链路通过独立验收后，在同一次重构中删除四个动作及其专用执行链，不把 deprecated 代码带入最终插件；
4. 删除动作工具、MySQL/SSH 专用执行器、专用审批文案、专用 schema、仅服务旧动作的 vendored 依赖和对应注册逻辑；
5. 普通 SSH 部署继续使用 Hermes terminal + 本机 OpenSSH。

不在通用注入未验收前提前删除，避免失去回归对照；但最终候选不得同时保留新旧两套产品逻辑。

### 10.1 必须删除的旧生产代码候选

以下文件/能力需要在实现计划阶段逐项做引用分析；若只服务旧固定动作，最终必须删除：

- `credential_guard/tools.py`
- `credential_guard/mysql_executor.py`
- `credential_guard/ssh_tools.py`
- `credential_guard/ssh_executor.py`
- 旧 `mysql_credential_action` / `ssh_credential_action` 注册与 CLI 自检代码
- 旧 `target + action` 审批展示和动作白名单
- 只为 MySQL 固定动作打包的 `deps/pymysql` 及发布清单项
- 旧双文件加载、交叉引用和敏感路径分支
- 只验证旧动作行为的单元测试、E2E 脚本、测试 companion 与文档

若其中某段通用安全逻辑仍被新架构使用，应先迁移到职责明确的新模块，再删除旧模块，不能以“还有一处 import”为理由整文件保留。

### 10.2 允许保留的通用能力

只有与最终产品方向一致并仍有调用证据的代码可以保留：

- 外发 registry、稳定逻辑引用和编码变体脱敏；
- 私钥与敏感路径保护；
- `llm_request`、`llm_execution`、`transform_tool_result` fail-closed 边界；
- 新单文件严格加载、审批绑定、TOCTOU 校验和通用注入器；
- 最终 ZIP、Provider wire、非干扰和发布身份验收框架。

### 10.3 清理完成判据

最终签收前必须同时满足：

1. 生产插件不再注册或暴露两个旧动作工具；
2. 生产包中不再包含只服务旧动作的 executor、PyMySQL 依赖和 companion；
3. 全仓搜索旧工具名、动作名、双文件名，只允许出现在历史 0.3.1 文档/迁移说明或明确的负向兼容测试中；
4. import 图中不存在无调用生产模块、循环兼容层或“暂时保留”的死分支；
5. 删除旧代码后全量、E2E、最终 ZIP 和双构建仍全部通过；
6. 最终发布 manifest 与源码清单证明旧文件未进入制品；
7. 独立代码审查必须单列“旧架构残留扫描”，发现无用代码即 BLOCKING。

## 11. 迁移方案

提供一次性本地迁移命令：

```text
hermes credential-guard migrate-config
```

迁移只做：

- 读取旧 `credentials.json` 和 `targets.json`；
- 生成新的 `credential-guard.json.tmp`；
- 严格校验；
- 显示不含真值的迁移摘要；
- 用户确认后原子重命名为 `credential-guard.json`；
- 旧文件改名为带时间戳的本地备份，不删除。

迁移失败不得产生半成品正式配置，也不得修改旧文件。

## 12. 失败策略

| 失败 | 处理 |
|---|---|
| 配置缺失、权限错误、JSON/Schema 错误 | 阻断 Provider 和含引用的工具执行 |
| 外发脱敏快照构造失败 | Provider 调用 0 次 |
| 未登记引用或悬空引用 | 工具执行 0 次 |
| 工具/参数位置不匹配 | 工具执行 0 次 |
| 目标不在 allowlist | 工具执行 0 次 |
| 用户拒绝、超时、审批异常 | 真值解析 0 次，工具执行 0 次 |
| 审批后配置变化 | 阻断并要求重新审批 |
| 注入失败 | 原工具调用 0 次 |
| 结果中仍有秘密或私钥 | 返回固定安全错误，不回流原结果 |

错误只返回固定错误码和安全说明，不返回异常对象、真值、原始参数副本或本地路径。

## 13. 实施里程碑

### R0：Hermes 插件接口命门验证

目标：先证明现有 Hermes `tool_request`、`pre_tool_call`、`tool_execution` 顺序能够满足“审批前不注入、审批后才注入”。

完成标准：

- 假工具收到的参数只在审批通过后包含诱饵真值；
- 审批页和 middleware trace 只含引用；
- 拒绝时真值解析和假工具调用均为 0；
- 不修改 Hermes 核心即可完成。

若接口顺序或审批数据流不满足，停止后续实现，先决定是否需要 Hermes 上游扩展；不能用 pre_tool_call 前注入来凑功能。

### R1：单文件配置与双文件迁移

目标：完成 `credential-guard.json` Schema、严格加载、单文件脱敏快照和原子迁移。

完成标准：

- 正反例覆盖权限、symlink、未知字段、重复/悬空引用、类型不匹配；
- 旧配置迁移成功且旧文件不被删除；
- 外发 wire 中所有诱饵和编码变体计数为 0。

### R2：通用引用识别、审批绑定和 TOCTOU

目标：模型可在工具参数中使用引用，审批与配置摘要、工具名和参数摘要绑定。

完成标准：

- 未审批时不解析真值；
- 修改工具名、参数、目标或配置后不能复用旧审批；
- 普通无引用工具调用行为与未安装插件一致。

### R3：安全注入适配器

目标：支持 HTTP Header、环境变量和 stdin 三种配置化注入。

完成标准：

- 新增 API/Jenkins 目标只改配置，不改插件；
- 真值不进入 Provider、审批、middleware trace、会话和工具结果；
- 目标错绑、重定向到未授权 host、Header 位置错误时阻断；
- 环境变量只存在于单次子进程，不污染 Hermes 进程全局环境。

### R4：统一结果守卫与非干扰

目标：所有正式工具结果在进入模型上下文前经过同一个权威守卫；能安全脱敏就保持原格式和业务含义返回，无法确认安全则用固定安全文本阻断原文，并证明普通工具能力不受影响。

详细方案与任务真源：

- `docs/R4-统一结果守卫与非干扰-落地方案.md`
- `docs/R4-统一结果守卫与非干扰-严格TDD实施计划.md`

完成标准：

- 已登记真值、支持编码变体、认证 Header/Cookie、明确敏感字段、异常栈和 PEM 残余均不能回流；
- 干净文本、JSON、日志和表格原样放行，不增加审批、不改变工具执行或副作用；
- 守卫异常或最终零残留复查失败时返回固定安全文本，不虚构成功、失败或回滚，不自动重试；
- 普通聊天、文件、Git、terminal、SSH、Docker/systemd、编码、测试和排障有真实非干扰证据；
- 全量测试 0 failed，0.3.1 冻结制品哈希不变，worker 未自动升级；
- 稳定候选冻结后，Cursor 与两路 Hermes 最终只读复审全部 PASS。

旧动作退场属于 R5；新发布收口属于 R6，不混入 R4。

## 14. 验收矩阵

### 14.1 必过正例

- 已登记凭证明文和编码变体外发均被引用替换；
- HTTP Bearer、Basic、API-Key Header 按配置注入到正确 host；
- 子进程环境变量和 stdin 仅在单次执行可见；
- SSH alias 部署不受影响；
- 普通无凭证的 terminal、文件、编码和测试流程不受影响；
- 凭证轮换后新请求使用新值，旧审批不可复用。

### 14.2 必过反例

- 引用发往攻击者域名；
- HTTP 30x 跳转到未授权 host；
- 引用位于未允许参数或聊天正文；
- 命令把引用用于 `echo`、文件写入、远端 printf 或 URL query；
- 审批拒绝/超时；
- 审批后配置变化；
- 配置权限错误、symlink、未知字段、重复或悬空引用；
- 注入器、脱敏器和结果守卫故障；
- 工具输出、错误栈或 Provider wire 残留真值；
- 试图读取统一配置、SSH 私钥或受保护路径。

### 14.3 真实框架验收

必须使用：

- 临时 HOME/HERMES_HOME；
- 合成诱饵凭证；
- loopback 假 Provider、HTTP 服务和假工具；

## 15. 版本策略

- 若保留旧动作兼容，可发兼容小版本；若删除旧工具/配置，则升主版本。

## 17. 本轮决策记录

已确认：

1. 插件核心从固定动作切换为“外发脱敏 + 审批后本地注入 + 结果脱敏”；
2. 业务扩展主要通过配置，不为每个场景修改插件；
3. 两个配置文件合并为一个本地敏感文件，但凭证与绑定逻辑分区保留；
4. 第一版选择“通用工具参数注入”，不解析普通聊天正文；
5. 默认审批页显示引用、凭证别名和允许目标，不显示真值；
6. 0.3.1 保持冻结，worker 暂不升级。

## 18. 用户评审重点

请重点确认四件事：
