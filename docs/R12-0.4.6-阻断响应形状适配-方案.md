## 1. 现象

`api_mode: anthropic_messages` 的用户触发任何一次本机阻断（fail-closed）时：

| 位置 | 用户实际看到的 |
|---|---|
| CLI 主输出 | `Invalid API response after 3 retries: response time 21.0s`，退出码 1 |
| 等待时间 | 约 20 秒（3 次重试 + 退避） |
| stderr | 仅 `DIAGNOSTIC_REASONS` 那段中文诊断（配置类失败才有） |
| **丢失的内容** | **`format_block_message()` 生成的六行阻断消息，含 `代码：CG-XXX`** |

对照组：填一个不存在的模型名 → `HTTP 503 无可用渠道`，原因清晰。**说明这不是宿主对所有失败的通用表现。**

### 1.1 危害定性

- **不泄密**。阻断本身成功了：Provider 调用次数 = 0，凭证没有外发。
- **属可用性 / 可诊断性缺陷**：把「本机安全阻断」伪装成「上游 API 故障」，把排查方向从"检查本机配置"引向"检查中转站/网络/限流"。
- 真实场景代价：`chmod 600` 就能解决的问题，用户可能先去排查半小时上游。

## 3. 与「README 诊断说明不准确」的关系（原清单第 2 项）

原判断：「README:893 说去找 `CG-CONFIG-UNAVAILABLE`，实测五种故障场景一次都没出现」。

**该判断不准确，本方案予以更正**：

- 该阻断码**确实存在**（`middleware.py:174`），由 `format_block_message()` 写入阻断响应体的 `代码：` 行。
- 之所以"从未出现"，正是因为**这条消息装在被本 bug 吞掉的那个响应体里**。
- stderr 里能看到的那段中文（`配置加载失败 / 文件 / 位置 / 原因 / 处理`）来自另一条独立通路 `_text_for_diagnostic_event()`（`middleware.py:391`），它不含 `代码：` 行。

**结论：清单第 1 项与第 2 项是同一个 bug 的两个症状。修复本项后，阻断码会正常出现在主输出，README 的原始表述即自动成立。**

README 已先行更新为准确描述（含「已知问题」提示块），本项修复合入后需回改该提示块。

## 4. 修法选型

### 方案 A：按 `api_mode` 分支构造（推荐）

```python
def _safe_blocked_response(detail=None, api_mode=None):
    ...
    if api_mode == "anthropic_messages":
        return _blocked_response_anthropic(text)
    return _blocked_response_openai(text)   # 现状，覆盖 chat_completions / bedrock
```

`on_llm_execution` 从 kwargs 取 `api_mode` 传下去。

| | |
|---|---|
| 优点 | 精确；不动已正确的 OpenAI/Bedrock 分支；下游 `normalize_response` 契约已由 F3 验证可用 |
| 缺点 | 未来新增 api_mode 需同步适配 |
| 风险 | 低。`api_mode` 拿不到时退化为现状（等价于当前行为，不会更糟） |

### 方案 B：单个对象同时携带 `choices` + `content`

| | |
|---|---|
| 优点 | 一劳永逸，不依赖 `api_mode` |
| 缺点 | 响应对象语义混乱；`normalize_response` 会同时看到两套数据，行为未验证；对未来 transport 的副作用不可预期 |
| 风险 | **中高**。属于"骗过校验"而非"符合契约" |

### 方案 C：A + B 兜底

`api_mode` 已知走 A；未知走 B。

| | |
|---|---|
| 优点 | 最稳 |
| 缺点 | 引入 B 的全部未验证风险，换取一个 F4 已证明不会发生的边界情况 |

### 推荐：**方案 A**

理由：F4 已证明 `api_mode` 稳定可得；F3 已证明 Anthropic 形状被下游正确消费；F5 已证明现有分支无需改动。B/C 的额外复杂度没有对应收益。

## 7. 覆盖范围决策（已定）

用户决策（2026-08-24）：**下限是 `anthropic_messages` + `chat_completions` 必须正确；
其余 api_mode 当前已经能用的，一律保持原样，不刻意收窄、不主动删除覆盖。**

核心原则：**本次是"补一条坏掉的分支"，不是"重划支持范围"。任何今天能正常工作的
api_mode，修复后必须依然正常工作。**

| api_mode | 当前 validate | 本次动作 | 修复后 |
|---|---|---|---|
| `anthropic_messages` | ❌ F5 = False | **新增专用分支** | ✅ 正常显示阻断消息 |
| `chat_completions` | ✅ F5 = True | 默认分支保持不动 + 回归护栏 | ✅ 不变 |
| `bedrock_converse` | ✅ F5 = True | **不动**，继续由默认分支覆盖 | ✅ 保留，不移除 |
| `codex_responses` | ❓ 本机 `ImportError`，无法取证 | **不动**，继续走默认分支 | ⚠️ 维持现状（既不改善也不退化） |

### 7.1 「不刻意适配 codex」的确切含义

**不是移除支持，是不新增针对性适配。** codex 继续走默认（OpenAI）分支，
行为与今天逐字节一致：

- **安全语义不变**：阻断依然成立，Provider 调用次数 = 0，凭证不外发。
- **可诊断性维持现状**：若 codex 用户触发阻断，仍可能看到
  `Invalid API response after N retries`，诊断需查 stderr。
  **这是本次未修复的既有状态，不是本次引入的退化。**
- 若将来 codex transport 可在本机取证，再按同样方式补一条分支即可，
  本方案的分支结构对此开放。

### 7.2 决策依据

1. 本机 `agent.transports.codex` 无法 `import CodexTransport`（实测 `ImportError`），
   **无法取证的适配等于凭空猜测**，违反"未验假设不写进方案"的原则。
2. 实测本机配置只用到一种 api_mode：

   ```
   custom_provider  ai-model-claude   api_mode = anthropic_messages
   model.provider   custom:ai-model-claude
   fallback_providers  []（空）
   auxiliary        全部 auto，跟随主 provider
   ```

3. `chat_completions` 覆盖绝大多数第三方/中转站场景，与 `anthropic_messages`
   合计即为实际使用面的下限要求。

### 7.3 零退化硬约束（新增护栏）

方案 A 的实现必须满足：**除 `anthropic_messages` 走新分支外，其余一切走原分支，
且原分支产出的对象与修复前逐字段一致。**

对应测试（§6.1 第 3 条强化）：

- `api_mode` 取 `None` / `"chat_completions"` / `"bedrock_converse"` /
  `"codex_responses"` / 任意未知字符串时，`_safe_blocked_response()` 的返回对象
  与修复前**逐字段相等**（含 `id` / `object` / `created` / `model` / `choices` 结构 / `usage`）。
- mutation：若把默认分支改成 Anthropic 形状，该测试必须转 RED。

**验收口径：不允许出现"为了修 Anthropic 而让别的 api_mode 变差"的情况。**

### 7.4 诚实披露要求

Release Notes 与 README 必须写明：**本次修复新增 `anthropic_messages` 分支；
`chat_completions`、`bedrock_converse` 等原有行为保持不变；`codex_responses`
未做针对性适配，其阻断消息显示问题维持现状。**
不得笼统宣称"修复了阻断显示问题"，也不得声称"缩小了支持范围"。
